# Длительная работа VPS

Команды выполняются в `~/margo`. Во всех примерах Compose:

```sh
docker compose -p margo -f docker-compose.yml -f docker-compose.vps.yml ...
```

В `.env` задайте отдельный случайный `MARGO_VERIFY_PASSWORD` и один канал:
`MARGO_ALERT_TELEGRAM_TOKEN` + `MARGO_ALERT_TELEGRAM_CHAT_ID` либо `MARGO_ALERT_WEBHOOK_URL`.
Webhook принимает HTTPS POST с JSON `{"text": "..."}`, без перенаправлений.
Секреты остаются в серверном `.env` с правами 600. Для Telegram предварительно откройте диалог с ботом.

После настройки выполните `config --quiet`, затем `up -d --build` с указанными выше файлами.
Проверьте `ps`, `logs --tail=50 backup monitor scheduler` и публичный `/health`.

## Проверка работоспособности

`/health` возвращает 200 с `{"status":"ok","database":"ok"}` только после запроса к БД
и чтения таблицы пользователей. При ошибке БД или отсутствии таблицы возвращает 503,
без текста исключения и реквизитов соединения. PostgreSQL-запросы ограничены тремя
секундами; ожидание соединения из пула и подключение тоже имеют тайм-ауты.

`monitor` раз в минуту проверяет публичный HTTPS `/health`, включая Caddy и сертификат.
Адрес можно переопределить через `MARGO_MONITOR_URL`. Он отдельно проверяет:

- heartbeat планировщика: тревога после 120 секунд без обновления;
- ошибки, пропуски и зависание заданий: назначение — максимум 15 минут между завершениями,
  пополнение — 25 часов, если включено и указан `WIKIMEDIA_USER_AGENT`;
- запас материалов ru/en: минимум между общим каталогом и остатками каждого пользователя,
  с теми же правилами исключения прочитанного и уже назначенного, что у рекомендаций;
- резервную копию: успешное восстановление не старше 25 часов.

Порог запаса — `MARGO_CATALOG_LOW_WATERMARK` (по умолчанию 60).
Ошибки отдельных пользователей и `status=error` от пополнения учитываются как сбои задания.
Состояние доставки сохраняется в Docker volume: уведомление при появлении проблемы,
напоминание раз в час и сообщение о восстановлении. Неудачная доставка повторяется
на следующем цикле. После запуска монитор ждёт минуту для старта остальных процессов.

## Резервные копии и проверка восстановления

`backup` выполняет `pg_dump -Fc` при запуске и каждые 24 часа после успешной копии.
После ошибки повторяет попытку через 5 минут. Перед признанием копии успешной он
восстанавливает её через `pg_restore --exit-on-error --single-transaction` в новую
случайную базу **отдельного** контейнера `restore-db`. Рабочий volume не подключается
к проверочному серверу. Индексы, ограничения и внешние ключи создаются заново.
После восстановления читаются версия миграций и количества записей в ключевых таблицах,
затем временная база удаляется.

Копии находятся в `./backups` (или `MARGO_BACKUP_DIR`), права файлов 600.
Рядом с `.dump` сохраняется JSON с SHA-256, временем и результатами восстановления;
`status.json` читает монитор. Незавершённые файлы имеют расширение `.partial`.
Старые `.dump` удаляются только после успешной новой копии, срок хранения по умолчанию
14 дней (`MARGO_BACKUP_RETENTION_DAYS`). Ошибка проверки сохраняет предыдущие копии.

Ручная копия, когда обычный `backup` остановлен (во избежание параллельных запусков):

```sh
docker compose -p margo -f docker-compose.yml -f docker-compose.vps.yml stop backup
docker compose -p margo -f docker-compose.yml -f docker-compose.vps.yml run --rm backup --once
docker compose -p margo -f docker-compose.yml -f docker-compose.vps.yml up -d backup
```

Повторно проверить выбранную копию без изменения рабочей БД:

```sh
docker compose -p margo -f docker-compose.yml -f docker-compose.vps.yml run --rm backup --verify /backups/margo-TIMESTAMP.dump
```

Для аварийного восстановления сначала остановите `api`, `scheduler`, `monitor`, `backup`.
Сохраните текущую базу, выберите проверенную копию и сверьте SHA-256. Восстановите её
в **новую** PostgreSQL-инстанцию версии 17 с `pg_restore --exit-on-error --single-transaction
--no-owner --no-acl`. Проверьте отчёт и API, переключите приложение на восстановленную
базу, примените нужные миграции и возобновите сервисы. Проверочный скрипт намеренно
не умеет перезаписывать production. Для новой инстанции отдельно создайте пользователя
и пароль из защищённого `.env`: `pg_dump` не сохраняет глобальные роли PostgreSQL.

## Границы текущей настройки

Копии оставлены на VPS по выбранной конфигурации. Потеря диска или всего VPS уничтожит
и данные, и копии. При суточном интервале возможна потеря примерно суток изменений;
PITR/WAL-архивирование не включено. Исходники, `.env`, HTTPS-конфигурация и пакеты
клиентов требуют отдельного сохранения.

Монитор работает отдельным процессом на том же VPS: он обнаруживает отказ API,
но не сможет отправить сообщение при полном отключении хоста или сети.
Для такого события нужен внешний монитор публичного `/health`.
Docker перезапускает завершившиеся процессы; статус `unhealthy` сам по себе не перезапускает контейнер.
