# Синхронизация и конфликты

Сервер — источник истины для статьи дня и профиля. Клиент не ранжирует статьи, не выбирает их без сети и всегда показывает дату загруженной рекомендации.

Локальная SQLite хранит JSON-снимки карточек/профиля/истории и отдельную FIFO-таблицу активных операций. Токен находится только в flutter_secure_storage. SQLite не содержит паролей или токенов. Один активный аккаунт; перед входом в другой активный кэш очищается, а неотправленные действия сохраняются отдельно для прежнего аккаунта. Другая база API не может получить токен или очередь текущего сервера.

## Протокол

Действие содержит UUID `operation_id`, `article_id`, `field`, `value`, `base_version`. Поля: `saved`, `feedback`, `read`. Запись операции и оптимистичного состояния выполняется одной SQLite-транзакцией. Повторная отправка сохраняет **исходный UUID и содержимое**.

Для `read=true` клиент также записывает в операцию `read_at` — исходное время события в UTC (ISO 8601). Эта же дата используется локально, при восстановлении очереди и после синхронизации. Сервер требует строку с часовым поясом, приводит её к UTC и отклоняет дату более чем на 5 минут в будущем (HTTP 422, весь пакет откатывается). Ненулевое `read_at` допустимо только для `read=true`; для снятия отметки оно не передаётся. Давность офлайн-событий не ограничена. Старые клиенты и уже сохранённые операции без `read_at` совместимы: для них остаётся время получения сервером. Их исходное время восстановить из операции невозможно. Повторное `read=true` сохраняет существующую дату; после снятия отметки новое прочтение получает время нового события.

Сервер в одной транзакции блокирует строку пользователя, применяет операции и сохраняет ответы в `sync_operations`. Ключ `(user_id, operation_id)` уникален. Повтор возвращает сохранённый ответ. Повторный UUID с иным содержимым возвращает 409. Неверный элемент откатывает весь пакет. Клиент снимает подтверждённые действия и сохраняет серверный снимок одной SQLite-транзакцией. Если процесс завершился до подтверждения, пакет будет отправлен повторно без повторного эффекта.

Клиент проверяет, что ответ содержит ровно одно подтверждение каждой отправленной операции. При неполном ответе очередь остаётся на устройстве, синхронизация завершается с понятной ошибкой вместо бесконечной повторной отправки. Смена сессии и HTTP-синхронизация сериализованы; устаревший ответ не может восстановить экран аккаунта после выхода. Действие, сделанное во время обновления, запрашивает дополнительную синхронизацию.

На PostgreSQL блокировка строки сериализует конкурентные запросы одного пользователя. Уникальные ограничения защищают назначение одной статьи на дату и от повторного назначения статьи. SQLite на сервере — только однопроцессный локальный режим разработки.

## Конфликты

У оценки, избранного и отметки прочтения **независимые счётчики версий**, а не часы устройства. Изменение применяется, только если `base_version` совпадает с версией соответствующего поля. При устаревшей версии побеждает сервер, ответ содержит `status: conflict`; клиент убирает операцию и сообщает о конфликте. Другие поля не теряются. Последующие офлайн-действия сравниваются отдельно по своим версиям. Поле `read` принимает `true` (отметить прочитанным) или `false` (снять отметку). При снятии `read_at` становится `null`, статья исключается из статистики прочтения и фильтра «Прочитанное». Повторное подтверждение `true` сохраняет дату, пока отметка не снята. Уже назначенная статья остаётся в истории и повторно не рекомендуется. Устаревшие изменения прочтения разрешаются по версии поля, как и оценки/избранное.

Оценки хранятся как текущее состояние, веса рассчитываются от базового профиля и текущих оценок; повторные запросы не суммируют вклад. `known` исключает статью из будущих назначений, не снижает тематический интерес. `difficult` также не снижает интерес: при ранжировании будущих статей применяется небольшой штраф за длительность (временная эвристика, не измерение сложности).

Настройки профиля изменяются только онлайн, с отдельной версией; при конфликте нужно синхронизировать профиль и повторить изменение. Выйти с неотправленными действиями нельзя, пока они не синхронизированы. Удаление аккаунта явно удаляет и такие действия. Экспорт возвращает подтверждённые серверные данные; сначала синхронизируйте очередь.

Подтверждённый ответ сохранения профиля сразу записывается в SQLite, до следующей синхронизации: обрыв связи после успешного PATCH не возвращает старые настройки. После входа профиль также загружается и сохраняется до отправки очереди, чтобы последующий сетевой сбой не оставлял авторизованную сессию на экране входа.

Синхронизация запускается при открытии приложения, возвращении в него, каждые 45 секунд и по кнопке. При 401 клиент удаляет активный кэш и токен, предварительно сохраняя неотправленные действия в отдельной очереди аккаунта. Очереди хранятся в SQLite в записях `account_outbox:…`, с ключом из адреса API и неизменяемого ID пользователя. Сохранение очереди и очистка активных данных выполняются одной транзакцией; изменение схемы существующей базы не требуется.

После успешной авторизации и проверки `/api/auth/me` восстанавливается только очередь того же аккаунта на том же сервере: исходный порядок, UUID, значения и базовые версии сохраняются. Восстановление очереди и оптимистичного состояния также атомарно. Далее запускается обычная синхронизация с прежними правилами подтверждений и конфликтов. Сетевой сбой, неудачный вход, деморежим, перезапуск приложения или вход в другой аккаунт не удаляют отложенные очереди. При запуске без токена оставшаяся активная очередь также сохраняется для повторного входа.

Успешное явное удаление аккаунта удаляет его активные неотправленные действия. Ответ 401 при попытке удаления не подтверждает удаление аккаунта, поэтому очередь сохраняется для повторной авторизации. Если аккаунт удалён с другого устройства, 401 сохраняет очередь, но восстановить её можно только после успешного входа с прежним ID; новый аккаунт с тем же email её не получит. Нет обещания очистки на навсегда отключённом устройстве: сервер не может связаться с ним.

## Уведомления

Ежедневное локальное напоминание создаётся по настройкам профиля, независимо от загруженной статьи и подключения к серверу. Оно приглашает открыть MARGO, а не сообщает о готовности конкретной карточки. Нажатие открывает «Сегодня»; для получения актуальной статьи нужна синхронизация с сервером.

Android использует ежедневный локальный inexact alarm, с разрешением POST_NOTIFICATIONS и ресиверами восстановления после перезагрузки. Windows использует системные toast-уведомления через flutter_local_notifications: клиент планирует 30 отдельных будущих напоминаний и продлевает расписание при открытии приложения или смене дня в работающем клиенте. Повторяющиеся уведомления Windows-плагин не поддерживает, поэтому после 30 дней без запуска расписание закончится.

При смене времени, часового пояса или аккаунта расписание перестраивается. Если время сегодня уже прошло, первое напоминание планируется на завтра. Отключение уведомлений, выход из аккаунта и деморежим отменяют расписание на устройстве. Настройки другого устройства применяются после синхронизации. Не используются точные alarms, гарантии минуты или постоянно работающий tray-процесс. Подробности и проверка доставки — в [инструкции по уведомлениям](notifications.md).

FCM/APNs не подключены: endpoint регистрации push-устройства возвращает 501, а не имитирует успешную доставку. Для их добавления нужны конфигурация приложения в платформенной службе, секреты сервера и отдельный отправщик. Локальный пакет не включает такие секреты.
