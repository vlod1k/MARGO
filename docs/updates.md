# Обновления MARGO (Windows и Android)

Начиная с 0.4.0+8 release-клиент автоматически проверяет манифест по адресу из UPDATE_MANIFEST_URL при запуске, возвращении в приложение и раз в час. Проверки ограничены одной в час; в **Профиль → Обновления приложения** можно проверить вручную. В debug-сборке проверка только ручная. Вход в аккаунт не требуется.

Новая версия скачивается в кэш. Прогресс и кнопка **Установить обновление** появляются над текущим экраном. Установка начинается по кнопке. Ошибки обновлений не блокируют использование приложения. Неполные файлы удаляются, корректный файл используется повторно. Перед установкой повторно проверяются размер и SHA-256.

На Windows запускается Inno Setup с текущей папкой приложения в качестве назначения. Установщик предлагает закрыть MARGO и запустить её после установки; принудительное закрытие и перезагрузка системы не используются. Работает и для переносимой сборки, если папка доступна для записи; установка добавляет приложение в список установленных программ. Локальная база и токен находятся вне папки приложения.

На Android используется системный установщик APK. При первом обновлении разрешите MARGO устанавливать приложения в открывшихся системных настройках, вернитесь и снова нажмите кнопку установки. Затем подтвердите обновление в системном окне. APK должен иметь прежний applicationId, ту же подпись и больший versionCode: клиент проверяет их перед передачей APK установщику. Удалять старую версию не нужно. Прежний ключ сохранён для совместимости; схема подписи и резервного копирования описана в [release-signing.md](release-signing.md).

Версии старше 0.4.0+8 не содержат механизма проверки: для перехода на первую версию с автообновлением потребуется один раз установить новый EXE/APK вручную поверх старого приложения.

## Подготовка выпуска

### Исправление Android 0.4.5+13 — 18 ноября 2026

В APK 0.4.4+12 ARM-снимки содержали старую форму восстановления и требование
пароля от 10 символов, хотя исходники и сервер уже принимали шестизначный код
и пароль от 8 символов. Проверка версии пакета и тесты исходников этого не выявили.
Android 0.4.5+13 собран после `flutter clean` и опубликован в существующем канале.
Сохранены applicationId и сертификат, versionCode увеличен до 13.

`build-android.ps1` теперь очищает сборку перед release.
`verify-android-account-access.ps1` проверяет актуальные сообщения формы внутри
`libapp.so` для armeabi-v7a, arm64-v8a и x86_64; проверка включена также в подготовку
обновлений и CI. Старый APK 0.4.4 отклоняется, новый проходит все три проверки.
Три теста формы восстановления прошли. APK повторно скачан с публичного HTTPS-адреса:
размер 65103872 байта, SHA-256 `5a5ff24dbfc641f054965c512292cabd32a9e7ca09358f37cfd500392110dbf3`.
Совместимость подписи проверена с APK 0.4.4; установка на физический телефон
в этой проверке не выполнялась.

### Общая процедура

1. Увеличьте `version` и номер сборки после `+` в `apps/margo_flutter/pubspec.yaml`. Для каждого выпуска номер сборки должен расти, даже при изменении основной версии.
2. Соберите обе платформы и установщик:

```powershell
./scripts/build-windows.ps1
./scripts/build-windows-installer.ps1
$env:MARGO_ANDROID_CERT_SHA256 = '47cdf9c65e2bd828b455430785c983ba6e50a804c8c06bd6f8c21e06900a52ad'
./scripts/build-android.ps1 -AllowLegacyDebugCertificate -PreviousApk .secrets/margo-signing/previous-0.4.3-11.apk
./scripts/prepare-updates.ps1 -Notes 'Описание изменений' -PreviousAndroidApk .secrets/margo-signing/previous-0.4.3-11.apk -AllowLegacyDebugCertificate
```

Сначала настройте Windows Authenticode и закреплённые отпечатки согласно [release-signing.md](release-signing.md). Последняя команда проверяет подписи, совместимость Android с предыдущим APK и версии внутри установщика и APK с pubspec, вычисляет SHA-256, копирует пакеты с уникальными именами в `backend/releases` и атомарно записывает `latest.json`. Старые пакеты сохраняются для клиентов, уже начавших загрузку. При необходимости задайте `-WindowsInstaller`, `-AndroidApk`, `-OutputDirectory`.

3. Разместите новые EXE/APK в каталоге `backend/releases` на сервере, **затем** замените `latest.json`. Не публикуйте манифест раньше пакетов. Подготовка файлов локально сама по себе не обновляет удалённый сервер.
4. FastAPI раздаёт этот каталог по `/updates` без авторизации. Docker Compose монтирует `./backend/releases` в API только для чтения. Для уже работающего сервера после изменения конфигурации один раз пересоздайте API. Без Docker каталог можно задать переменной `MARGO_RELEASES_DIR`.
5. Проверьте HTTPS-адрес `/updates/latest.json` и ссылки из него с другого устройства. Клиент принимает только HTTPS-пакеты с того же origin в `/updates/`, без перенаправлений. SHA-256 подтверждает целостность, доверие к источнику обеспечивается HTTPS и доступом к серверу. Публичный Windows-установщик должен пройти проверку Authenticode перед подготовкой манифеста.

Для другого сервера передайте Flutter `--dart-define=UPDATE_MANIFEST_URL=https://your-domain/updates/latest.json` при сборке обеих платформ. `API_BASE_URL` задаётся независимо. Ни манифест, ни пакеты не должны содержать секреты.

Настоящая установка обновления на физическом Android и замена запущенного Windows-приложения требуют отдельной проверки на устройствах; тесты загрузки и сборки не подтверждают этот сценарий.
